# Frozen campaign discovery and CI headroom

The main-branch repeat after PR #226 exceeded the frontend job's existing five-minute budget. Its Vitest worker passed all 70 assigned files and 5,299 tests in 248.17 seconds; the concurrent deployment worker was still running the 26-case archive method when GitHub cancelled the job. Eight other jobs succeeded. Successful PR CI and identical merged-main trees do not make that cancelled repeat successful.

The first proposed correction split inventory/archive cases, but its actual x86 timings exposed three older monolithic campaigns: lifecycle (102.602 seconds), anchored review (48.896 seconds), and authenticated review (37.485 seconds). The deployment worker completed 292.6 seconds of work before another deadline cancellation; its Vitest worker had passed in 252.08 seconds. ARM passed in 238 seconds. This rejected profile is retained. A request to stop the obsolete workflow was denied by the GitHub token; no access was expanded and no automatic retry was requested.

`ci_case_discovery.install` now registers all **199 frozen cases across seven authenticated campaigns** as distinct asynchronous unittest methods. Every method retains its exact fixture ID, expected outcome, body, integrity checks and cleanup. Duplicate, malformed or colliding identities are rejected before class mutation. The original case bodies are structurally identical; frozen lists, policies, native reports, report graders and runtime sources remain unchanged.

`campaign_test_assets.share_immutable_assets` restores the original campaign's reuse of unchanged package/model fixture assets. Their bytes, physical identities, ownership, permissions and links are checked before and after each case. A changed asset fails qualification. Accounts, sessions, keys, journals, work roots, clients, application authorization and event loops remain fresh per case. Services, decisions and integrity verdicts are never cached. Existing unrelated classes retain their fresh setup lifecycle unless explicitly opted in. Native qualification is unchanged.

The complete, committed deployment manifest must equal fresh discovery. Both existing sequential deployment workers use stable test-ID partitioning: closed frozen-case IDs have a 2:3 x86/ARM hash weighting based on observed runner cost; ordinary contracts retain the original half partition. Remove the old whole-campaign placement overrides. Contracts require every frozen case exactly once and both lanes to cover each campaign. Seven old methods become 199; four helper contracts bring the total from **630 to 826**. This is a change in test granularity, not 199 new product capabilities.

Each worker emits a public test ID at start and its elapsed seconds at completion. The final report retains every executed ID and per-case duration. Interrupted output identifies its last admitted case without dumping configuration, credentials, source text or private evidence.

The nine jobs, two workers per frontend lane, runner architectures, one frontend production build, 139 frontend files, 10,532 frontend tests, job/step caps and retry policy remain unchanged. There is no new runner or automatic rerun. Unit scratch remains separate from native durability qualification.

Acceptance requires complete/disjoint manifest execution, all nine checks on the exact proposed head, and at least 30 seconds of reserve for frontend, frontend-history, backend job, backend test step and graph-runtime job. Merge uses the tested head as a lease; independently fetched main must have the same full tree. Record successful PR CI, rejected historical profiles and new main-push CI separately.

The independently authorized staged-reader binding and withdrawal-fence cutover remains the next product slice. This prerequisite creates no binding, enrollment, provider call, inference, deployment or legal-review decision.
