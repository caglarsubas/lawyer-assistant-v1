# Guarded carried-arrival-preserving exact-event handoff

A lawyer can explicitly prepare the original selected historical review from a
fresh private portfolio comparison while preserving the original carried arrival.
R03/R05 remain partial; this increment establishes private navigation behavior.

## Exact intent and fixed observations

`private-carried-arrival-event-handoff-v1` contains the original validated
CarriedArrivalReturn, a reduced fresh queue comparison, the stable preparation
snapshot and both one-record read timestamps. Every earlier receipt, arrival,
queue, preparation, unknown baseline and selected packet stays unchanged. No
predecessor windows, source bodies, quotations, review notes, matter titles or
recursively appended handoffs are retained.

Preserve exact customer OR, workspace date field/range, source-record dates,
bucket, matter/analysis/context, frozen evidence version/manifest and selected
event/packet. A changed head establishes neither a path, legal effect, approval,
replacement selection nor an unobserved intermediate version.

## Preparation and destination

Require an observed target in the current authorized bounded queue, its existing
exact-event GET and successful carried-arrival reconciliation. Current head and
version must be known, identities verified, tools available and current context,
selected-event and head admissions complete. Historical unknowns and pending
states remain unchanged; navigation cannot repair or promote them.

Explicit preparation reads the same selected-event endpoint exactly twice with
`window=1`. Require stable reduced identities against the fresh queue and both
reads, monotonic times/revisions, exact scope/evidence and all retained selected
and same-known-head packet pins. Check the current request fence and live token
before and after each await. A failed, drifting, denied or retired first read
stops the second; no automatic retry occurs.

Validate purpose and exact selected target before destination GET. Alternate
events, context-only targets and renewal/review redirects are rejected. A new
token remounts even for the same event. The existing single fresh exact-event GET
is compared independently against the new preparation and original carried
arrival, checking all earlier pins. Unknown identities and pending destination
admissions remain explicit. The disclosure shows separate metadata snapshots;
source tools keep their existing independent authorization/evidence checks.

## Return and confidentiality

Verified explicit return restores the original CarriedArrivalReturn unchanged.
No additional arrival is captured implicitly. Unavailable/loading/failed/denied/
blocked/retired metadata yields selection only. Partial, conflicting or
substituted metadata is rejected without fallback, repair or replay.

New filters/window/preparation, portfolio revision, target/token, scope/principal,
expiry and navigation retire pending replies and links. Late or denied data
cannot reopen details or dispatch follow-up reads. Validate before token
allocation/eviction; clone input/output. Keep eight principal-local memory
entries and thirty-minute expiry, opaque URL tokens and no browser storage.
Reload and principal loss close the contract.

Require current explicit same-firm matter content grants; customer tags confer
no permission. No new backend endpoint/schema, automatic source-body read,
review/renewal/export write, provider call, public graph update or deployment
change is introduced.
